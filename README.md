# 图片批处理（img-batch）

一次把**一批图片**收拾干净：**裁剪 → 旋转翻转 → 改尺寸 → 加水印 → 转格式压缩 → 压到指定体积**，
六个步骤按固定顺序走，每个步骤都有独立开关，只跑你开的那几步，处理完自动打包成一个 ZIP 下载。

> **纯本地处理 · 文件不上传 · 断网可用** —— 所有运算都在你自己的浏览器里完成，图片不会离开这台设备。

## 它一共七项能力

| 2 | **裁剪** | **可以直接拖的裁剪框**：拖框内 = 移动，拖 8 个手柄 = 缩放；比例锁在预设上（原图比例 / 1:1 / 3:4 / 4:3 / 16:9 / 9:16 / 21:9 / 自定义宽高），框内有三等分参考线、框外变暗，带「居中 / 重置 / 覆盖全部」；支持触屏拖动。另有一个「四周各裁掉 N 像素」的简单模式 |
| 3 | **旋转 / 翻转** | 顺 90° / 180° / 270°，任意角度（带底色可选：白 / 黑 / 自定义色），水平翻转、垂直翻转；界面里写清了 EXIF 自动摆正的真实情况 |
| 4 | **改尺寸** | 按长边 / 按短边 / 指定宽 × 高 / 按百分比 / 装在框内（contain，不裁切）；重采样质量 高 / 中 / 快；「不放大」开关 |
| 5 | **水印** | 文字水印或透明 PNG 图片水印；九宫格位置 + 平铺整张图；不透明度、旋转角度、边距；字号 / 大小按图片短边百分比（大图小图效果一致） |
| 6 | **输出格式与质量** | 保持原格式 / JPG / PNG / WebP；JPG 与 WebP 的画质滑块（40~100）；**透明图转 JPG 的背景色**；一张表逐条标清「有没有在原有基础上再掉画质」（含「PNG 作目标不新增损失」「裁剪 / 90° 旋转不重采样」这些容易写错的细节） |
| 7 | **输出与导出** | 剥掉元数据（EXIF / 备注 / 定位）；**压到指定体积**（自动试画质逼近，压不到会如实告诉你）；输出文件名后缀可改（默认 `_out`）；一键打包 ZIP，或只下载当前这一张；批量结束显示张数 / 成功失败 / 总体积变化 |

## 三步上手

1. **选图片**：把图拖到第一个框里（或点一下选择，或直接 `Ctrl + V` 粘贴截图）。
2. **打开要做的步骤**：左边 ① ~ ⑤ 五张卡片，每张右上角有个「启用」勾选框 —— **只勾你要做的**；
   旁边的 **▸** 可以展开 / 收起（**5 块默认全部收起**，只留编号 + 名称 + 启用 + 一行摘要，想看哪块再展开 —— 这样右边的效果预览一直看得到）。
   每块标题栏还有一个 **「↺ 默认」**，只把那一块恢复出厂设置（并把该块的「启用」关掉）；想全部重来用底部的 **「全部恢复默认」**。
3. **调参数**：裁剪就直接拖那个框（拖框内 = 移动，拖 8 个手柄 = 缩放，比例锁住不会拉变形）；水印位置用九宫格点。
   参数一改，右边的**处理前 / 处理后对比预览**立刻更新。
4. **导出**：点「一键处理全部 → 打包下载 ZIP」，浏览器自动下载一个 `img-batch_日期_时间.zip`。

> 只想导出当前预览的那一张？点「只下载当前这张」。
> 想中途停？点「取消」，当前这张处理完就停，已经处理好的照样打包给你。

## 参数说明（都是大白话）

| 参数 | 是什么意思 |
|---|---|
| 裁剪框 | 就是图上那个带 8 个小方块的框：**拖框内 = 移动，拖小方块 = 缩放**。框里的两条线是三等分参考线，框外变暗的部分会被裁掉 |
| 固定比例 | 框的长宽比锁在这个值上，怎么拖都不会变形；选「原图比例」就是跟原图一个长宽比 |
| 框能拖多小 | 有下限（大约画面的 2%），拖到最小也不会变形、也不会跑出画面。想裁得比这更小，直接用「四周各裁掉 N 像素」那项 |
| 批量时的固定比例 | **每张图各自按这个比例取**：框的中心位置与「占同比例最大块的比例」整队统一，具体像素按各自画面换算。所以一批比例不同的图跑「1:1」，**出来的每一张都真的是正方形**（不会只有碰巧是 4:3 的那张才对）。界面上那行「裁剪后导出 W × H」与真正导出的尺寸走**同一个函数**，两边不会对不上 |
| 居中 / 重置 | 「居中」= 框大小不变、挪到正中间；「重置」= 按当前比例重新取最大的一块、居中 |
| 覆盖全部 | 一键把框拉到整张图（等于不裁），想反悔的时候用 |
| 四周各裁掉 N 像素 | 均匀裁掉一圈边框，适合去截图边框、扫描件黑边；填 0 就用上面的百分比 |
| 任意角度 + 空白处底色 | 转过之后四角会空出背景，这个颜色就是填那个空的 |
| 按长边 / 短边 | "最长的那条边不超过 N 像素"，手机壁纸、网页配图都这么设 |
| 装在框内 | 整张图等比缩进你给的框里，**不裁切**、不变形；框比图大就保持原尺寸（不放大） |
| 重采样质量 | 缩放时的插值算法。高 = 最清楚但稍慢，快 = 最省时间但边缘会糙一点 |
| 不放大 | 原图本来就比目标小的时候，保持原尺寸不动（避免把糊图拉得更糊） |
| 字号（水印） | 水印在图上占多大，**按图片短边的百分比**算，大图小图效果一致 |
| 平铺 | 水印斜着一排排铺满整张图，适合防搬运；勾上后九宫格位置就不起作用了 |
| 边距 | 水印离图片边缘留多少空，同样按短边百分比算 |
| 剥掉元数据 | 删掉图片里藏的拍摄信息（相机型号、拍摄时间、GPS 定位、备注）。**这一步本身不损失画质** |
| 目标体积 | 自动反复试画质，尽量压到不超过这个值；实在压不到会给最大的合理结果 + 明确提示 |
| 文件名后缀 | 输出名多出来的一截，默认 `_out`（`照片.jpg` → `照片_out.jpg`）；留空就不加 |

## ⚠️ 哪些组合是无损的（这条最容易被含糊过去，所以说清楚）

| 原格式 → 目标格式 | 画面改过之后（裁剪 / 旋转 / 改尺寸 / 加水印） | 画面原封不动时 |
|---|---|---|
| PNG → PNG | **无损**（PNG 是无损容器 + 无损编码） | **无损**（直接在原字节上剥，不重编码） |
| PNG → WebP | 有损（走画质参数重编码） | 有损 |
| PNG → JPG | 有损 | 有损 |
| JPG → JPG | **有损**（解码再编码掉一次画质） | **无损**（只在原字节上剥元数据） |
| JPG → PNG | **不新增损失**（见下方第 2 点） | 会重编码（换了格式就没法只剥元数据） |
| JPG → WebP | 有损 | 有损 |
| WebP → WebP | 有损 | **无损**（剥 EXIF / XMP 块，不动像素） |
| WebP → JPG | 有损 | 有损 |
| WebP → PNG | **不新增损失**（见下方第 2 点） | 会重编码（换了格式就没法只剥元数据） |

几点必须掰清楚的：

1. **「画面原封不动时」这一列分两种情况**：
   - **目标格式 = 原格式**（PNG → PNG / JPG → JPG / WebP → WebP）且勾了「剥掉元数据」→ 走**字节级**剥离，一个像素都不重新编码，**无损**；
   - **目标格式换成了别的**（例如 JPG → PNG）→ 必须重新编码一次，这时只有 PNG 作目标才「不新增损失」。
2. **PNG 作目标时不会「新增」损失**。把已经解码出来的像素存成 PNG，用的是无损编码，所以 JPG → PNG、WebP → PNG 不会比原图更差，也不会额外掉画质。但它也**救不回**原图在有损压缩时已经丢掉的细节 —— 而且体积通常会明显变大（JPG 转 PNG 尤其明显）。所以表格里写的是「**不新增损失**」，不是「无损」。
3. **「画面改过」这一列里，PNG 作目标时要看你做了什么操作**：
   - **裁剪**、**90° / 180° / 270° 旋转**、**翻转**都是像素级搬运、不重采样 → 配 PNG 输出**不新增损失**；
   - **改尺寸**（重采样）、**任意角度旋转**、**加水印**（要重绘像素）→ 会重采样 / 重绘，这一环是有损的。
   
   ⚠️ 但要注意：如果原图本来就是 JPG / WebP，那它在被压缩的那一刻就已经损失过了 —— 后面无论做什么、存成什么，都救不回来（只是「不再新增」而已）。
4. **JPG / WebP 作目标时，只要重新编码就必然再掉一次画质**（解码 → 画布 → 再编码），PNG → WebP 也一样，因为浏览器编码 WebP 走的是「画质」参数。
5. **只有「画面原封不动 + 目标格式 = 原格式 + 勾了剥元数据」这一种情况**才可能一个像素都不重编码 —— 这时候是直接对原始文件字节动刀。

## 输出说明

- **保持原格式**：JPG 还是 JPG、PNG 还是 PNG、WebP 还是 WebP；画面没改又只勾了「剥掉元数据」时，会走**字节级路径**，一个像素都不重新编码。
- **透明图转 JPG**：透明处会被填色（默认白色，可以自己选）。JPG 格式本身不支持透明。
- 极个别情况下浏览器编不出你要的格式时会自动退回 PNG，扩展名跟着实际格式走，并在结果里注明，不会生成打不开的文件。
- ZIP 里的中文文件名正常显示（文件名按 UTF-8 写入）。
- 打包体积超过约 1.2 GB 时会拒绝打包并提示分批（ZIP 格式要求所有结果同时在内存里）。

## 性能与内存

这个工具是**一张一张顺序处理**的，不是一次性把所有图都读进内存：

- 同一时刻只解码 1 张原图，画完立刻把 Canvas 和 ImageBitmap 释放掉；
- 列表里只保留 160 像素的小缩略图，不保留大图；
- 预览用一张缩小到 1000 像素以内的小画布跑**同一套处理代码**，所以你看到的就是会导出的效果；
- **裁剪框与预览都按「画布的实际尺寸」算几何**，不是按原图像素硬算 —— 所以缩小预览里的裁剪范围、长宽比跟导出一模一样（这条有回归测试钉着）；
- 每张处理完会让出一次浏览器主线程，进度条能实时刷新，页面不会假死；
- 参数变化时预览会重新算一次当前这张（有防抖，不会一边拖滑块一边卡）；
- 桌面端右边的「效果预览 + 批量导出」是**吸附（sticky）**的：左边往下滚着改参数，右边一直看得到效果；再加上功能块默认收起，改参数时不会被一堆控件挤下去。

**单张长边超过 4000 像素**会标上「大图」提示：能处理，但会更慢、更吃内存，建议一次别放太多张。

## 已知限制

- 不支持 GIF、HEIC、AVIF、BMP 等格式（浏览器能不能解码就用不了），拖进来会被跳过。手机相册里的 HEIC 照片请先转成 JPG。
- WebP **输出**依赖浏览器编码器（Chrome / Edge / Firefox 都支持；个别旧浏览器会自动退回 PNG）。
- 「剥掉元数据」是最粗暴的剥法：JPG 里除了 JFIF 之外的 APPn 段和注释全丢，PNG 里 tEXt / zTXt / iTXt / tIME / eXIf 全丢，WebP 里 EXIF / XMP 块全丢。ICC 色彩描述文件也在被丢的范围内，**对色彩管理有严格要求的图请先备份原件**。
- 「压到指定体积」在目标格式是 PNG 时压不动质量，只能靠缩尺寸，代码里会明确提示改用 JPG / WebP。
- 裁剪框是用 **Pointer 事件 + `touch-action:none`** 实现的，鼠标和触屏都能拖；但触屏上**手指会挡住一部分画面**，精细对位建议改用鼠标 / 触控笔，或先放大页面。
- 超大尺寸图片受浏览器单张 Canvas 上限约束（Chrome 约 16384 像素），超过这一张会处理失败并标「失败」，但不会中断整批 —— 别的图照常处理、照常打包。遇到这种图先单独缩一次尺寸再用它。
- 界面里的预览是缩小显示的；水印在预览时会按屏幕大小放大到可见（不然大图缩到屏幕上小水印根本看不见），**导出时用的是严格按短边百分比算的真实比例**。
- 打包用的是最朴素的 store 模式 ZIP（不压缩），所以 ZIP 体积约等于所有输出图的体积之和；单条目超过 4 GB 或条目数超过 65535 需要 ZIP64，本工具不支持（图片场景到不了）。
- 没有撤销功能：处理是不可逆的，**建议先拿一两张试参数，确认了再整批跑**。原图不会被改动。
- 功能块的**折叠状态与各步骤参数会记在本机浏览器里**（`localStorage`，只存设置、不存图片），下次打开自动恢复；底部的 **「全部恢复默认」** 可以一键清掉，每个块标题栏的 **「↺ 默认」** 只重置那一块（并把该块的「启用」关掉）。折叠只影响显示，**不参与处理参数**，也不会写进任何导出结果。

**`file://` 下（双击打开）能用的功能**：选图、拖拽、`Ctrl + V` 粘贴、预览、批量处理、打包下载 —— 全部可用，不需要联网。

## 技术实现

- **零依赖单文件**：CSS / JS 全部内联在 `index.html` 里，没有构建步骤、没有 CDN、没有第三方库、**不用 ES module**（所以 `file://` 双击就能跑）。
- **图片解码**：优先 `createImageBitmap(file, { imageOrientation:'from-image' })`（按 EXIF 方向解码），失败退回 `Image` + `URL.createObjectURL`。
- **EXIF 方向**：工具自己解析 JPEG 的 EXIF Orientation 标签和 SOF 里的存储宽高，跟解码出来的宽高对比，**实测**告诉你这个浏览器有没有真的摆正（不是抄一句"浏览器会自动处理"）。
- **处理流水线**：解码 → 裁剪 → 旋转翻转 → 改尺寸 → 加水印 → 编码，裁剪与缩放用 `drawImage` 的 9 参数形式一步完成，尽量少一次中转。
- **裁剪框**：归一化坐标（0~1）的伸缩框，用 Pointer 事件 + `touch-action:none` 驱动；移动 / 8 方向缩放 / 比例锁定 / 边界夹紧都是纯函数，全部有单测。
- **固定比例的批量正确性**：归一化框本身是"跟图片比例相关"的，所以选固定比例时，**每张图都会按自己的像素尺寸重新解一次**（保留中心与相对大小），并且解出来的是**像素级精确**的整数宽高 —— 一批里每张都严格是选定比例，不会出现"某张碰巧对、别的都不对"。
- **界面与导出同一个事实源**：裁剪框的尺寸用一个「占同比例最大块的比例」（`frac`）表达，编辑器显示、预览、批量导出**全都只走 `cropRect()` 这一个函数**。所以界面上写「裁剪后导出 600 × 600」，导出来就一定是 600 × 600（这条有端到端对账测试盯着）。框对象内部一律**整体搬运**（改尺寸只改宽高、其它字段原样保留）；万一出现"固定比例却没有比例信息"的内部不一致，会**直接报错**而不是悄悄按当前图估算 —— 否则一批图里大部分碰巧正确、个别出错，极难发现。
- **预览＝导出**：几何按**传进来的画布实际尺寸**计算，预览的小画布和导出的原图共用同一套公式，所以相对裁剪范围与长宽比完全一致（有跨尺度的回归测试）。
- **水印绘制**：`fillText` / `strokeText` / `shadowBlur` / `globalAlpha` / 平铺 + 旋转坐标系。
- **元数据剥离**：JPG / WebP 走字节级裁剪（不重编码）；PNG 会丢元数据块 + 重做行滤波 + 用 `CompressionStream('deflate')` 重压，**真无损**。
- **目标体积**：在画质档位上做**二分查找**，最多 24 次尝试，先试你设的最高画质，够小就不降；压不到就回退到最小结果并如实说明。
- **ZIP 打包**：自己实现的 store 模式 ZIP（CRC32 查表 + 本地文件头 + 中央目录 + EOCD），文件名带 UTF-8 标记位，不引入任何压缩库。
- **可测性**：纯计算集中在一段标记注释里（可被 Node 脚本抽出来单测）；处理引擎有独立标记（可整段抽到 Node 里配 canvas 替身真跑流水线）；ZIP 引擎有独立标记（喂假数据跑真 ZIP，再用 Python `zipfile` 交叉验证）；整段内联 JS 还能在一个假 DOM 上完整启动一次，验证初始化不抛错、折叠不影响执行参数。

## 隐私说明

- 所有处理都在浏览器本地完成，图片**不会**上传到任何服务器；
- 没有后端、没有数据库、没有统计代码，页面不发任何网络请求；
- 把 `index.html` 存到本地，断网（拔网线 / 关 Wi-Fi）也能照常使用；
- 代码全部在这一个文件里，可以自己打开查看，也可以用浏览器开发者工具的 Network 面板确认没有任何请求。
